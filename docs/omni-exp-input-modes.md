# Omni-exp input modes and demo video

Lets the omni-exp UI take its visual/audio input from more than the live camera,
so the user can demo the full pipeline — tasks extracted from a stream, the
background core ("CC") working them, results coming back and spoken — without
talking into the mic live.

## Input modes

Five modes, each selectable before connecting (and changeable after disconnect).
Every mode feeds the same pipeline: `#cam` → canvas → `sendFrame()` (1 Hz JPEG
over WS) + audio → 16 kHz PCM16 audio over WS. Only the **source** changes.

| Mode | Input | When to use |
|------|-------|-------------|
| Live camera (default) | `getUserMedia` mic+cam | Real interaction |
| Local video | `<input type=file>` | Offline demos, your own recording |
| Video URL (VOD) | `.mp4` / `.webm` link | Quick demo from any hosted file |
| Live stream | HLS `.m3u8` (or anything that plays) | Continuous live-like demo |
| Demo reel | auto-loads generated clip | One-click "show me everything" |

The **Demo reel** button on the login screen sets the mode and starts connecting
in one click.

## How video modes feed the same pipeline

The camera is just `<video id="cam">` + canvas + audio graph. Video modes reuse
that exact structure — only the source changes:

- **Frames:** `sendFrame()` already draws whatever is in `#cam` to a canvas and
  sends it as a 640px JPEG at 1 Hz. No change needed; a `<video>` element with a
  local file or URL is frame-extractable the same way a camera is.
- **Audio:** Camera mode uses `audioCtx.createMediaStreamSource(stream)` →
  `ScriptProcessor` → 16 kHz downsample → WS. Video modes use
  `createMediaElementSource(cam)` for the same chain. The `<video>` element must
  stay **muted** so autoplay policy doesn't block it — `createMediaElementSource`
  still sees the audio even when muted. When the user mutes the video, the audio
  stream goes silent, so no separate "mute mic" is needed for video modes.
- **Loop:** a per-mode toggle for live stream and replay; off by default for VOD.

### hls.js for live streams on Chrome

Safari plays HLS natively; Chrome does not. The client loads
[hls.js](https://github.com/video-dev/hls.js) (via CDN `unpkg.com`) only when a
live stream URL is selected, and attaches it to `#cam`. When hls.js can't load or
the URL plays natively, the client falls back to plain `cam.src = url`. The
library is only fetched once per session and only if a stream is picked — no build
step, no added latency for other modes.

## Demo video

Generated by `scripts/make-omni-demo-video.sh` (macOS only, uses `say` + ffmpeg +
Pillow). Outputs a single MP4 with:

- **9 clearly-actionable tasks** spoken aloud (distinct enough to pass the agent's
  `normalize_work_task` dedup, which keys on a 180 s window)
- On-screen text showing each task + a progress counter (2/9 etc.)
- 16 kHz mono audio (matches the client's mic path exactly)
- ~40 s total; each task has a 1.2 s silence gap

Default output: `state/omni-demo/omni-tasks-demo.mp4`.

### Running the demo

```bash
# 1. Generate the demo video (if you haven't yet)
bash scripts/make-omni-demo-video.sh

# 2. Run the agent in normal mode (NOT the default OMNI_EXP_MODE=demo)
OMNI_EXP_MODE=normal_with_gui .venv/bin/python3 src/omni-exp-agent.py

# 3. Open the UI, click "Demo reel", and connect.
#    The video will play, tasks appear, CC works them in the background.
```

**Important:** The agent's default `OMNI_EXP_MODE=demo` makes `work` render an
HTML page, not execute real tasks. For a task-pipeline demo, always use
`normal_with_gui` (or `no_gui`).

## Static route for the demo video

`src/omni-exp-agent.py` serves the generated demo at
`/omni-demo/omni-tasks-demo.mp4` from `state/omni-demo/`. This is a small static
file handler — no authentication required (the WS connection is already
authenticated). The login screen's "Demo reel" button references this path.

## Browser notes

- **Autoplay policy:** video elements in `#cam` stay muted so autoplay never
  blocks. Audio is captured via `MediaElementSource` regardless of mute state.
- **Safari:** HLS plays natively, AudioContext unlock is needed on first tap.
- **Chrome:** hls.js is fetched dynamically only if live stream mode is selected.
- **Firefox:** same as Chrome; hls.js handles HLS.
